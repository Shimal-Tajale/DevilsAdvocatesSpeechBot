Overview
We're building an AI speech coach with a physical robot body. It watches and listens while you present, reacts live (LEDs, head movements, an LCD, a beep), and coaches you with spoken and on-screen feedback afterward.
One-line pitch: a robot practice audience that helps you show up for the people you care about (a wedding toast, a class talk, a eulogy, a first conversation) by reacting while you speak and coaching you with measurable feedback.
Event: HackTX 26 (Freetail Hackers), Oct 24–25, 2026. Tracks are announced; see Target tracks below.
Goals
A working end-to-end demo: someone speaks, the robot reacts live, then the bot gives specific, scored feedback.
Feedback built from real measurements (pace, filler words, pauses, posture, eye contact), not generic AI praise.
Every teammate owns a visible piece of the final product.
Non-goals
Streaming everything perfectly in real time. Post-speech analysis is the baseline, and live alerts are layered on top.
User accounts, auth or polish beyond what the demo shows.
A complex robot. A head, lights, a screen and a buzzer are enough.

Working rules
Shimal and Kundansai share one FastAPI app but separate files. Shimal's pipeline exposes run_session(audio), and Kundansai's routes call it.
Check-ins every 3–4 hours: what works, what's blocked, what to cut.
Shimal makes the final call on scope cuts, after hearing the owner.
Git
One repo with folders backend/, frontend/, bridge/, robot/ and docs/. Each person works mainly in their own folder.
Short-lived branches (shimal/pipeline, abhiram/frontend). Merge into main every 1–2 hours, whenever something works. No PR reviews.
Pull from main before merging, test that it runs, then push. main must always run. If it breaks, fix or revert right away.
.env stays out of Git. Commit only .env.example with key names.
System architecture

system architecture · 6 parts, one hub
No part talks to another directly. Everything goes through the hub, so the robot, the database or any API can be swapped or dropped without breaking the rest.
Data flow for one speech
The robot's PIR sensor sends P:1 → bridge → hub broadcasts user_present → the frontend opens the session.
During the speech, the browser runs vision and volume checks and sends alert events to the hub, which relays them to the robot.
At the end, the browser POSTs the recording to /speech. The hub calls Deepgram, computes metrics, calls the AI model and TTS, saves to Postgres and broadcasts the results.
The frontend shows the scorecard. The robot lights up, shows the score and speaks its tip.
Backend
One FastAPI app is the hub. It runs the speech pipeline, keeps session state and relays every event to everything connected.

Pipeline (run_session)
Broadcast state: thinking.
Transcribe with Deepgram (pre-recorded, filler words on, word timestamps).
Compute metrics in our own Python: words per minute, filler count and list, pauses over 2 s, longest pause, speaking time.
Merge vision stats reported by the browser during the speech (posture alerts, eye-contact %, gesture level).
Get feedback from the AI model using Abhiram's rubric. It must return JSON (schema below).
Broadcast feedback, then lcd with the score, then state: speaking.
Speak the robot_line with text-to-speech (browser speechSynthesis as fallback).
Save everything to Postgres, then broadcast state: idle.
Feedback JSON (AI model output)
{
  "scores": {"structure": 7, "clarity": 8, "delivery": 6, "persuasion": 7, "confidence": 6},
  "overall": 68,
  "strengths": ["Strong opening hook"],
  "fixes": ["Cut 'um' before key points", "Pause after your main claim"],
  "robot_line": "Great hook! Next time, slow down in the middle."
}
AI provider switch: start on Gemini and move to Muse Spark for the Meta track. All provider code lives in get_feedback(), so switching is one line in .env.
PROVIDER = os.getenv("AI_PROVIDER", "gemini")

def get_feedback(transcript, metrics, rubric) -> dict:
    prompt = build_prompt(transcript, metrics, rubric)
    raw = call_muse(prompt) if PROVIDER == "muse" else call_gemini(prompt)
    return parse_feedback_json(raw)

Rules for live alerts
Only fire if the behavior lasts about 2 s.
At most one alert of each kind every 12 s.
During a speech the robot never talks. It uses lights, movement, the LCD and a beep. It speaks only at the end, or when its hand is called on.
Frontend and computer vision
The Ionic app is what judges see on screen. Vision runs in the browser, so live alerts never wait on the server.
Screens (Abhiram)
Start: pick a mode and type a topic. A "step up" prompt, which also triggers when the robot sees someone.
Live: webcam preview with a pose overlay, a recording timer, live alert toasts and a volume meter.
Scorecard: overall score, rubric bars, strengths and fixes, a transcript with filler words highlighted, and pace over time.
History: past sessions for a speaker, to show improvement.

Audio in the browser: record with MediaRecorder and POST to /speech at the end. Measure volume live with the Web Audio API to raise too_quiet alerts.
Calibration: at the start, the speaker stands naturally for 3 s and every check compares against that baseline. Smooth every signal over about 1 s.
Camera: the MLH webcams are gone. Use a phone as the webcam (Continuity Camera on iPhone + Mac, DroidCam or Iriun otherwise), at chest height with the upper body in frame. If the vision page runs on the phone itself, open it through the ngrok https:// URL, because phones only allow camera access on https or localhost.
Replay mode (guaranteed demo): upload a recorded video and play it in a <video> element. MediaPipe analyzes it while it plays, so alerts fire in sync and the robot reacts as if it were live. The vision code takes any video source (camera or file), so both modes share one code path. Record 1–2 demo videos early: slouching, "um"s, hands in pockets.
Robot hardware
The robot is an Arduino Mega connected to a laptop over USB. The Mega has no WiFi or Bluetooth, so all commands go through bridge.py.
Parts on hand (Abhijay's order): ELEGOO Mega 2560 R3 Most Complete Starter Kit + ELEGOO 37-in-1 Sensor Modules Kit. Confirm the box contents (servo count, LCD, breadboard, wires, power module).
From the MLH hardware lab (ask early, these run out): the JBL Go 3 speaker, so the robot's voice comes from its body; a Grove servo for the arm if the kit has only one; spare breadboard and jumper wires.

Notes
Close the Arduino IDE Serial Monitor before running the bridge. Only one program can use the port at a time.
Abhijay can test alone by typing S:thinking into the Serial Monitor. No server needed.
If a servo jitters or the board resets, power the servos from the kit's power module instead of the Mega's 5V pin.
Don't use the kit's sound sensors for speech. They only measure loudness.

Prompt rules
Give the model the measured numbers. It explains them; it doesn't guess them.
Every fix quotes or points to a specific moment.
Return JSON only, in the schema from the Backend section.
Keep robot_line short and friendly. It's spoken aloud.
Add-ons
Add-ons start only after the MVP demo works end to end. Each one reuses the existing event bus, so most are small.
Raise hand to speak (signature add-on)
The robot behaves like a real audience member: it raises its hand with a question, waits to be called on, then asks.
Trigger. Simple version: after the speech ends, the AI picks the weakest claim and writes one audience question. Stretch version: with Deepgram streaming, the server sends the last ~30 s of transcript to the AI model every ~20 s and asks "is there a question worth raising?"
Raise. Server sends hand: raise. The arm servo goes up, the LED pulses and the frontend shows "Robot has a question."
Wait to be called on. The robot waits until the speaker pauses for 2+ s, says a phrase like "yes?", or clicks "Take question."
Ask. Server sends hand: lower, then speaks the question with TTS. The speaker's answer is recorded and scored as a mini-session.

Timeline and cut rules

24-hour plan · 4 phases, 3 gates
Hour 12 is the gate that matters. If one full speech doesn't work end to end by then, every add-on waits.
Cut rules (agreed at kickoff)
Hour 12, hardware go/no-go: if the robot doesn't respond to live events, switch to the on-screen avatar. Abhijay moves to testing and Devpost.
Hour 12, live alerts: if vision is unreliable, keep posture only and drop eye contact.
Hour 18, feature freeze: after this, only bug fixes and demo polish.
Any time: a feature that blocks the MVP for over 1 hour gets cut or simplified. Shimal makes the call after hearing the owner.

Demo script (about 3 min)
Abhiram steps up. The robot wakes (PIR), turns its head and lights blue.
He starts a 45 s speech and slouches on purpose. The robot shakes its head, the LED goes red and the LCD says "Stand tall!"
He says "um" a few times. The buzzer beeps and the LCD counter goes up.
He finishes. The robot raises its hand, gets called on and asks a sharp question about his weakest claim.
The scorecard appears: overall score, rubric bars, highlighted fillers. The robot speaks its one-line coaching tip.
Pitch (Shimal leads)
Problem: the moments that bring people together (toasts, talks, first conversations) are the ones people dread speaking in, and coaching is expensive and rare.
Product: a robot practice audience that reacts live and gives measurable feedback, so you show up confident for the real audience.
Why it's credible: scores come from measured behavior. The rubric is built from Abhiram's real TEDx coaching experience.
Tech: custom metrics, live computer vision, Meta's Muse models, an event-driven pipeline and real hardware.
Responsible design: audio and video aren't stored without consent.
Next: wedding toasts, classrooms, debate teams, interview prep.
